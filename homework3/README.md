## 二、串口反馈格式说明

数据包校验通过并应用设置后、以及按键改变运行状态或方向后，单片机通过串口回传一帧 ASCII 文本：

```
STATE=RUN,DIR=FWD,STEP=300,LED=1
```

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `STATE` | `RUN` / `PAUSE` | 当前运行状态 |
| `DIR` | `FWD` / `REV` | 流水方向，正向 / 反向 |
| `STEP` | 100~2000 | 相邻 LED 切换间隔，单位 ms，十进制 |
| `LED` | 1 / 2 / 3 | 当前点亮的 LED 编号（从 1 开始，与丝印一致） |

- 发送由 DMA 完成（`HAL_UART_Transmit_DMA()`），上一帧未发完时只保留最新一帧挂起，发完立刻补发，不会堆积过期状态。

## 三、选做说明

### 1. 硬件 I²C 驱动 OLED

- CubeMX 配置 I2C2：PB10 = SCL、PB11 = SDA，100 kHz，地址 0x3C。
- 与软件 I²C 版共用同一套 `oled.c`，用宏 `OLED_USE_HW_I2C` 切换：`1` = 硬件（当前配置），`0` = 软件 I²C。
- 发送超时 100 ms，屏没接好也不会卡住启动；上电自动探测 0x3C / 0x3D，串口打印 `OLED:OK addr=0x3C` 便于确认接线。

### 2. 串口反馈改用 DMA 发送

- 用 CubeMX 为 USART1_TX 配置 DMA1_Channel4（存储器→外设、字节对齐、普通模式），`__HAL_LINKDMA` 在 `HAL_UART_MspInit` 中完成绑定，DMA1_Channel4 中断已使能。
- 发送入口 `Uart_StartTx()` 由 `HAL_UART_Transmit_IT()` 换成 `HAL_UART_Transmit_DMA()`；发送缓冲为静态数组，传输完成前不会被改写。
- 传输结束后 HAL 走 `UART_DMATransmitCplt → HAL_UART_TxCpltCallback`，回调里只清忙标志（事件记录），是否补发下一帧由主循环的 `Uart_Task()` 判断，符合"中断只做事件记录"的要求。
- 反馈内容与功能要求和基础版一致：`STATE / DIR / STEP / LED` 四个字段，触发时机也相同。

## 四、思考题

**题目：当流水灯的切换间隔较长时（如 2000 ms），有没有出现按下按键和发送串口指令时不能立刻执行、有一定的延迟？如果有，思考问题出在哪里，可以怎样改进？**

### 1. 一种原因是阻塞延时：等待期间 CPU 被占死，延迟正比于间隔


```c
while (1)
{
  LED_Next();          /* 换下一颗灯 */
  HAL_Delay(step_ms);  /* 间隔 2000 ms 就在这里原地等 2000 ms */
}
```

这 2000 ms 里 CPU 一直卡在 `HAL_Delay()` 的计数循环中，主循环一次都不转，于是：

- **按键扫描停摆**：程序根本没去读 GPIO。按下的时刻如果落在延时中间，这一采样点就永远错过了；按得短一点，可能整个"按下—松开"都没被看到；按得久一点，也要等延时结束才生效，最多晚一个间隔（2 秒），还容易被当成一次长按处理。
- **串口指令被拖着**：即使开了接收中断，中断里也只是把字节存下来，解析、校验、更新状态、回显都在主循环，同样要等延时结束。这期间上位机如果连发几包，接收缓冲填满后新字节只能丢掉。
- 表现就是"按了没反应、发指令要等半天才动"，而且间隔设得越长越明显——延迟直接正比于 `step_ms`。

### 2. 解决这个问题方法：换灯用时间戳，不用延时

```c
void LedFlow_Tick(uint32_t now_ms)
{
  if (!s_state.running) return;

  if ((uint32_t)(now_ms - s_last_tick) >= s_state.step_ms)
  {
    s_last_tick += s_state.step_ms;
    LedFlow_Step();            /* 到点才换灯，没到点立刻返回 */
  }
}
```

- `LedFlow_Tick()` 只是比较一次时间差就返回，主循环一直高速空转，**2000 ms 和 300 ms 对按键和串口的响应速度没有区别**。
